# Ферма рилсов: пачка роликов → апрув → Trial Reels

Дизайн от 19.08.2026. Заменяет спеку `2026-07-28-islamic-reels-content-factory-design.md`
в части сборки и постинга: та строила конвейер на n8n + Creatomate с банком хуков и
циклом победителей, эта — простой бот на существующей инфраструктуре.

## Задача

Вы отдаёте боту пачку: N видео-подложек и N блоков текста (хук + описание). Бот
накладывает хук на подложку, присылает готовый ролик в Telegram и спрашивает апрув.
Одобренные раскладывает по слотам и сам публикует в Trial Reels аккаунта
`@daristeppe` — по 15 в день, без вашего участия.

Trial Reels — это публикации, которые видят только не-подписчики. Выпуск удачного
ролика в основную ленту остаётся ручным решением в приложении Instagram
(`graduation_strategy: MANUAL`).

## Что решено и почему

| Решение | Причина |
|---|---|
| Пары 1:1 — хук + своя подложка | Метод из видео-источника; подложка не переиспользуется, IG не бустит один файл дважды |
| Живём в проекте `qurany`, боте отчётов | У бота может быть только один вебхук; отдельный проект потребовал бы второго бота и второй копии IG-токена |
| Чтение — через Instagram Login, публикация — через Facebook Login | Проверка 19.08 показала: `trial_params` принимается на `graph.facebook.com`. Отчётный бот остаётся на своём токене нетронутым, ферма получает свой — под публикацию |
| ffmpeg в функции, по ролику за вызов | Рендер 1080×1920/30 с ≈ 20–40 с CPU — влезает в лимит вызова с запасом; новой среды исполнения не нужно |
| Апрув по одному, заливка по слотам | 30 одобрений за вечер превращаются в два дня публикаций без вашего участия |
| Правка ✏️ меняет только описание | Хук вжарен в пиксели: его правка — это новый рендер и новый файл. Плох хук → ❌ и в следующую пачку |
| Оборванная заливка не повторяется | Дубль рилса на аккаунте хуже потерянного поста |
| Исходник удаляется сразу после рендера | На Hobby превышение лимитов Blob отключает хранилище на 30 дней, а не выставляет счёт |

## Схема

```
/batch  →  ссылка на страницу (HMAC, 30 мин)
              ↓
      N видео → прямо в Blob (мимо функции, multipart)
      N блоков текста → /api/farm/start
              ↓
      batch + N item-файлов в Blob, статус pending
              ↓
РЕНДЕР  /api/farm/render  (цепочка тиков, 1–2 ролика за вызов)
      ffmpeg → Blob → в чат с кнопками → review
      исходник удаляется
              ↓
АПРУВ   вебхук /api/telegram (callback_query)
      ✅ → queued + слот | ❌ → rejected | ✏️ → editing → review
              ↓
ПОСТИНГ /api/farm/post  (внешний таймер раз в 15 мин)
      контейнер REELS + trial_params → опрос → publish
      → в чат «залил 7/30» + permalink → posted, ролик удаляется
              ↓
СУТКИ   /api/farm/daily  (cron Vercel)
      уборка, снятие застрявших, добор просроченных
```

## Данные

Всё файлами в существующем Blob store `qurany-snapshots`, префикс `farm/` —
рядом с `snapshots/` и `state/`, не смешиваясь с ними.

```
farm/batches/<batchId>.json      { batchId, chatId, threadId, createdAt, total }
farm/items/<itemId>.json         состояние одного ролика
farm/sources/<batchId>/<n>.mp4   подложка (удаляется после рендера)
farm/out/<itemId>.mp4            готовый ролик (удаляется после заливки)
```

Один файл на ролик, а не один на пачку: в Blob нет compare-and-set, и две
параллельные цепочки затирали бы друг другу состояние соседних роликов.

```ts
type ItemStatus =
  | "pending" | "rendering"   // до отправки в чат
  | "review"                  // кнопки висят, ждём решения
  | "editing"                 // ждём ответ с новым описанием
  | "rejected"
  | "queued"                  // одобрен, ждёт слота
  | "posting" | "posted"
  | "failed";

interface Item {
  itemId: string; batchId: string;
  chatId: number; threadId: number | null;
  index: number;              // 7 из 30 — номер видно в чате и в ошибках
  hook: string; caption: string;
  sourceUrl: string; videoUrl: string | null;
  messageId: number | null;   // сообщение с кнопками
  editPromptId: number | null;// сообщение force_reply, по нему ищем ролик при правке
  status: ItemStatus;
  renderingAt: string | null; // отметки «работа началась» — против зависших статусов
  postingAt: string | null;
  scheduledAt: string | null; // слот заливки, ISO
  igMediaId: string | null; permalink: string | null;
  error: string | null; createdAt: string;
}
```

`renderingAt` и `postingAt` — приём из `dub-bot`: вызов функции умирает молча, и без
отметки времени ролик застрял бы в промежуточном статусе навсегда. Отметка старше
300 с (максимум жизни вызова) означает, что работа мертва и её можно перехватить.

## Вход

`/batch` в чате → ссылка `/farm/<token>`, живёт 30 минут. Токен — HMAC с зашитыми
`chatId`, `threadId` и сроком; нигде не хранится (`lib/tokens.ts` из `dub-bot`).

Страница: выбор файлов (`multiple`) и одно поле текста. Блоки разделены строкой
`---`, **первая строка блока — хук, остальное — описание**:

```
Jangan tunggu Ramadan untuk mulai
Setiap hari cuma 1 juz, dibaca bareng
satu grup. Yang mau ikut, tulis...
---
Kamu sibuk? Justru itu alasannya
Ada cara baca Qur'an yang...
```

Одно поле, а не два: количество хуков и описаний невозможно рассинхронить.

Валидация до загрузки — чтобы проблема не всплывала после N залитых файлов:

| Проверка | Порог | Причина |
|---|---|---|
| блоков = файлов | точно | пары 1:1 |
| хук | ≤ 3 строк по ~20 знаков | иначе не читается и не влезает в верхнюю треть |
| описание | ≤ 2200 знаков | лимит подписи Instagram |
| файл | ≤ 60 МБ | `/tmp` функции: исходник + результат |
| пачка целиком | ≤ 1 ГБ | квота Blob на Hobby; больше — предложить разбить на две |
| файлов | ≤ 50 | предохранитель от «выбрал всю папку» |

Файлы уезжают в Blob напрямую из браузера (`multipart`, по 3 параллельно, прогресс
«12/30») — через функцию 30 файлов не прошли бы. Затем `/api/farm/start` проверяет
токен, убеждается через `head()`, что каждый файл действительно в нашем хранилище,
создаёт batch и N item-файлов, пишет в чат «взял пачку: 30 роликов» и запускает
цепочку рендера. Любой отказ после загрузки удаляет залитые файлы — иначе они
останутся в хранилище навсегда.

## Рендер

ffmpeg и ffprobe — пакеты `ffmpeg-static` / `ffprobe-static`, в бандл роута попадают
через `outputFileTracingIncludes`. Бинарник в git не коммитим. Шрифт — один TTF в
`assets/hook.ttf`, туда же.

```
ffmpeg -i <подложка> [-f lavfi -i anullsrc]        # тишина, если у исходника нет звука
  -vf "scale=1080:1920:force_original_aspect_ratio=increase,
       crop=1080:1920,
       drawtext=fontfile=assets/hook.ttf:textfile=/tmp/<id>.txt:
                fontsize=64:fontcolor=white:
                borderw=6:bordercolor=black@0.9:
                line_spacing=12:x=(w-text_w)/2:y=h*0.18"
  -c:v libx264 -preset veryfast -crf 23 -pix_fmt yuv420p -r 30
  -c:a aac -b:a 128k -movflags +faststart -t 90 <результат>
```

**Текст через `textfile=`, а не в строку фильтра.** Символы `:` `'` `%` `\` и запятая
ломают разбор фильтра, а апострофы в индонезийском (`Qur'an`) встречаются постоянно.
Файл читается как есть — экранирование не нужно вовсе.

**`scale=...:increase` + `crop`, а не `pad`.** Исходники будут разного формата; кадр
заполняется целиком, чёрных полос не будет никогда. Цена — обрезанные боковины у
горизонтального исходника; для подложки это правильный компромисс.

**Перенос строк считается в коде.** `drawtext` не переносит сам, длинный хук уехал бы
за кадр. Жадный перенос по словам, ≤ 20 знаков в строке, максимум 3 строки. Хук, не
влезающий в эти рамки, не проходит валидацию на странице, поэтому рендер с ним не
столкнётся.

Роут `/api/farm/render?batch=<id>&key=<hmac>`, `maxDuration = 300`, бюджет цикла
240 с; следующий ролик берём только при остатке ≥ 150 с, иначе дёргаем себя заново.
Запас именно такой из-за потолка `-t 90`: тридцатисекундная подложка укладывается в
20–40 с, а девяностосекундная — в 60–120 с, и с меньшим резервом такой ролик упирался
бы в лимит вызова уже с отметкой `rendering`.

Пачка из 30 растягивается на ~20 минут, и первые ролики приходят в чат сразу — апрув
идёт параллельно рендеру.

**Упавший ролик не роняет пачку.** Ненулевой код возврата ffmpeg → item в `failed`, в
чат «ролик 7/30 не собрался: <хвост stderr>», цикл идёт к восьмому.

В чат уходит видео с подписью: номер `7/30`, хук, описание. Подпись к видео в Telegram
ограничена 1024 знаками против 2200 в Instagram, поэтому описание в подписи обрезается
до ~700 знаков — полный текст ваш собственный и целиком уходит в IG. Ролик при crf 23
весит 5–15 МБ, то есть отправляется дешёвым путём по URL; тяжелее 20 МБ — файлом
(`sendVideoUpload` уже написан).

## Апрув

Кнопки `[✅ Залить] [❌ Выкинуть] [✏️ Текст]`, `callback_data` вида `a:<itemId>`
(38 байт из разрешённых 64).

Вебхук `/api/telegram` дополняется разбором `callback_query`: проверка чата,
**обязательный** `answerCallbackQuery` (иначе у клиента вечный спиннер), снятие кнопок
и переписывание подписи на итог — «✅ в очереди на 20 авг, 09:00».

Повторное нажатие безопасно: ролик не в `review` → «уже обработано» и снятие кнопок.
Вы листаете чат вверх и жмёте по второму разу — это норма, а не ошибка.

❌ — удаляет готовый ролик из Blob сразу.

✏️ — бот присылает сообщение с `force_reply` и ставит `editing`; ваш ответ находится по
`reply_to_message.message_id` (он же `editPromptId`), описание заменяется, ролик
возвращается в `review` с кнопками. Отдельный статус нужен, чтобы `/reels` и таймер не
считали ролик ожидающим апрува.

### Команды

К одиннадцати существующим добавляются две:

- `/batch` — ссылка на страницу загрузки пачки (30 минут).
- `/reels` — состояние фермы: сколько ждёт апрува, сколько в очереди, когда ближайший
  слот, что упало. Заодно пинает цепочку рендера, если та оборвалась — приём из
  `dub-bot`, где ту же роль играет `/status`.

Роут `/api/telegram` сейчас — 203 строки на 11 команд с проверкой чата по
`TELEGRAM_CHAT_ID`. Добавлять в него `/batch`, кнопки и правку «ещё одним if» нельзя,
поэтому в работу входит вынос диспетчера команд в `lib/commands.ts` по образцу
`dub-bot` — без этого файл становится нечитаемым.

## Слоты и таймер

Окно с 09:00 Asia/Jakarta, интервал 45 минут, 15 слотов в день, последний 19:30.

При ✅ ролик получает ближайший свободный слот: не раньше чем через 5 минут, не занятый
другим `queued`/`posted`. Кончились слоты на сегодня — 09:00 завтра. 30 одобренных за
вечер сами раскладываются на два дня.

**Таймер внешний.** Vercel Hobby даёт 2 крона на проект и только суточное расписание —
«каждые 15 минут» на нём нет. Поэтому cron-job.org (или UptimeRobot) раз в 15 минут
дёргает `/api/farm/post?key=<hmac>`. Ключ в URL — HMAC-секрет; даже при утечке чужой
запрос способен лишь запустить заливку уже одобренных вами роликов по их же
расписанию.

Второй контур — суточный крон `/api/farm/daily`: добирает просроченные `queued`, если
внешний таймер лежал. Потеря внешнего сервиса означает сбитый ритм внутри дня, но не
потерянные публикации.

Первый крон проекта занят отчётом (`/api/report`, 5:45). После `/api/farm/daily` оба
слота Hobby заняты — запаса не остаётся.

## Заливка

```
queued, слот наступил
  → posting, postingAt = now
  → POST https://graph.facebook.com/v23.0/<FARM_IG_ID>/media
       media_type=REELS, video_url=<blob>, caption=<описание>,
       trial_params={"graduation_strategy":"MANUAL"}
  → GET /<container>?fields=status_code каждые 10 с (до ~4 мин)
       IN_PROGRESS → ждём | ERROR/EXPIRED → failed + в чат
  → FINISHED: POST /<FARM_IG_ID>/media_publish {creation_id}
  → GET /<mediaId>?fields=permalink
  → в чат «залил 7/30: <ссылка>», posted, ролик удаляется из Blob
```

За тик — не больше одного ролика: опрос контейнера занимает минуты, а слоты разнесены
на 45 минут. Просрочилось два — второй уедет следующим тиком.

Лимит Instagram — 100 публикаций за 24 часа; наши 15 в день от него далеко.

**Оборванная заливка не повторяется.** Если вызов умер сразу после `media_publish`,
ролик уже в Instagram, а у нас записано `posting`. Перехват такого ролика (отметка
старше 300 с) переводит его в `failed` с сообщением «заливка оборвалась, проверь ленту —
возможно, ролик уже опубликован». Дубль на аккаунте хуже потерянного поста; та же
логика уже принята в `dub-bot` для доставки видео.

### Токен публикации

Ферма ходит в `graph.facebook.com` и живёт на **собственном** токене `FARM_IG_TOKEN`,
отдельном от `IG_ACCESS_TOKEN` отчётного бота. Разделение вынужденное и полезное:
пути авторизации разные (Instagram Login против Facebook Login), а отчёты при этом
вообще не затрагиваются — они читают как читали.

Нужные разрешения: `instagram_basic`, `instagram_content_publish`, `pages_show_list`,
`pages_read_engagement`, `business_management`. App Review не требуется, пока
публикуем на собственный аккаунт с ролью админа приложения.

Токен из Graph API Explorer живёт час-два и годится только для проверок. Ферме нужен
долгоживущий: короткий обменивается на 60-дневный через
`GET /oauth/access_token?grant_type=fb_exchange_token` с `client_id` и `client_secret`,
после чего Page-токен, полученный по нему, не истекает вовсе. Продление и хранение —
как у отчётного бота: значение из env, зеркало в Blob, суточная проверка срока.

`FARM_IG_ID` — id аккаунта публикации; для `daristeppe` это `17841413773053161`
(связанная страница Facebook — «Видео из Фото»).

## Ошибки

| Где ломается | Реакция |
|---|---|
| Блоков ≠ файлов, хук не влезает, файл тяжёлый | Страница не даёт отправить — до загрузки |
| ffmpeg упал | Этот ролик в `failed` с хвостом stderr в чат, пачка идёт дальше |
| Цепочка рендера оборвалась | `/reels` пинает её, суточный крон добивает |
| Telegram не принял видео | Одна повторная попытка, потом ссылка на файл текстом |
| Контейнер IG вернул ERROR | `failed` + точный текст ошибки Meta в чат |
| IG отказал по правам или `trial_params` | `failed` + полный ответ API в чат — по нему решаем, нужен ли переезд на Facebook Login |
| Токен не продлился | Сообщение в чат сразу: молча умерший токен останавливает заливку навсегда |
| Заливка оборвалась после `media_publish` | `failed` + «проверь ленту»; заново не публикуем |
| Blob уперся в квоту | Сообщение в чат; на Hobby это отключение хранилища на 30 дней, а не счёт |

## Уборка — `/api/farm/daily`

Удаляет файлы `posted`/`rejected`/`failed` старше 3 дней · снимает застрявшие
`rendering`/`posting` старше 30 минут в `failed` с сообщением в чат · удаляет подложки
без item (осиротевшие после сорванного `/api/farm/start`) · добирает просроченные
`queued`.

Отдельно — ролики, зависшие в `review` или `editing` **старше 7 дней**: переводятся в
`rejected`, файл удаляется, в чат идёт список номеров. Без этого правила неотвеченные
ролики копили бы в хранилище по 15 МБ каждый и висели в `/reels` вечно. Семь дней —
запас на отпуск; хук, не одобренный за неделю, всё равно неактуален.

## Переменные окружения

Добавляются к существующим в проекте `qurany`:

```
FARM_TOKEN_SECRET        HMAC для ссылки загрузки, тиков рендера и внешнего таймера
FARM_IG_TOKEN            долгоживущий токен публикации (Facebook Login)
FARM_IG_ID               id аккаунта публикации: 17841413773053161 (daristeppe)
FARM_FB_APP_ID           для обмена короткого токена на 60-дневный
FARM_FB_APP_SECRET       туда же
FARM_SLOT_START=09:00    начало окна публикаций
FARM_SLOT_MINUTES=45     интервал между слотами
FARM_SLOTS_PER_DAY=15    сколько роликов в день
FARM_TZ=Asia/Jakarta     часовой пояс окна
```

`IG_ACCESS_TOKEN` и `IG_USER_ID` ферма не трогает — они остаются отчётному боту.
