# Hard ship

Жёсткая оркестрация: код пишут соннеты под опус-дирижёром, потом опус-QA ломает
результат, соннеты чинят, и только после этого работа отдаётся человеку — с
поднятым приложением и фактическим выводом команд, а не с обещаниями.

## Когда применять

Есть **одобренная** спека или план, и человек попросил оркестрацию. Без одобренного
плана этот скилл не запускается: дирижёр разнесёт по исполнителям непонятую задачу
быстрее, чем один агент успеет задать уточняющий вопрос.

Не применять для правки в один файл, для отладки одного бага и для чего угодно, что
дешевле сделать самому — 20 агентов на однострочник это не тщательность, а трата.

## Гейт до запуска

1. Рабочее дерево чистое или изменения осознанные: `git status --short`. Агенты
   будут писать в те же файлы; неучтённые локальные правки перемешаются с их
   работой.
2. Базовый прогон тестов **до** всякой работы: запусти тест-команду проекта и
   запомни вывод. Без базовой линии нельзя отличить сломанное агентами от
   сломанного заранее.
3. Скажи человеку одной строкой: сколько воркфлоу, примерная ширина, и что это
   дорого по токенам. Если в сессии стоит ограничение размера воркфлоу («Dynamic
   workflow size» в /config), назови его — оно ограничит ширину, и лучше узнать об
   этом до запуска, чем в логах.

## Шаг 1. Реализация — воркфлоу `hard-build`

Запускать **по `scriptPath`, не по имени**: `.claude/workflows/` в проекте харнесс
не регистрирует, по имени находятся только встроенные воркфлоу.

```
Workflow({ scriptPath: '<корень репозитория>/.claude/workflows/hard-build.js', args: {
  task: '<одна фраза: что реализуем>',
  specPath: 'docs/superpowers/specs/<файл>.md',
  testCommand: '<тест-команда проекта>',
  maxRounds: 4,
  maxItemsPerRound: 4,
}})
```

Внутри: опус-дирижёр читает спеку и репозиторий, возвращает план из
самодостаточных задач с **непересекающимися** списками файлов; скрипт спавнит по
соннету на задачу (пересечения разводит по волнам, чтобы двое не писали в один
файл); по каждой задаче независимый опус-ревьюер проверяет результат фактами.
Следующий раунд дирижёр планирует, уже видя приговоры ревьюеров, и закрывает работу
сам, когда претензий не осталось.

Прочитай `converged` и `closedBy` в результате:

- `conductor-done` — дирижёр закрыл работу, идём дальше.
- `maxRounds` / `budget` / `conductor-lost` — **не** делай вид, что всё хорошо.
  Скажи человеку, на чём остановились и что осталось в `openFindings`, и спроси,
  добавить раунды или разбираться руками.

## Шаг 2. QA — воркфлоу `hard-qa`

```
Workflow({ scriptPath: '<корень репозитория>/.claude/workflows/hard-qa.js', args: {
  target: '<что именно проверяем>',
  specPath: '<та же спека>',
  testCommand: '<тест-команда>',
  maxRounds: 3,
}})
```

Внутри: четыре опус-агента бьют по своим измерениям (юниты, сквозные пути,
нагрузка и параллелизм, краевые случаи), каждый пишет тесты только в свой
namespace и **не правит продакшн-код**; находки группируются по файлам, соннет
чинит файл целиком, независимый опус-верификатор воспроизводит дефект заново и
подтверждает или возвращает его в работу. Цикл идёт, пока не будет двух тихих
раундов подряд.

Разбирая результат, различай три исхода: `fixed` (доказано верификатором), `open`
(осталось), `refused` (исполнитель обоснованно счёл находку ошибочной — это
нормальный исход, но прочитай обоснование сам и согласись или нет).

Если `open` не пуст, а раунды кончились — запусти `hard-qa` ещё раз или скажи
человеку правду. Молча закрыть глаза на открытые дефекты нельзя.

## Шаг 3. Поднять и потрогать — руками, самому

Воркфлоу закончились, дальше работает главный агент. Никакой субагент не может
подтвердить, что приложение живое, — это делается здесь.

1. Подними то, что должно работать: сервер, дев-сборку, фронт. Если в проекте есть
   скилл на запуск (`run` или проектный) — им, иначе командой проекта в фоне.
2. Пройди основной путь по-настоящему: дёрни эндпоинты, открой страницу,
   отправь тестовый запрос. Для веба — браузером через доступный скилл, если он
   есть.
3. Прогони тесты целиком ещё раз и сравни с базовой линией из гейта.
4. Загаси то, что поднимал.

## Шаг 4. Отдать человеку

Отчёт в таком порядке: что теперь работает и **чем это доказано** (вывод команд,
не пересказ) · что осталось открытым и почему · что решено сознательно не делать ·
сколько раундов заняло. Открытые дефекты и обход проблемы называются вслух, даже
если всё остальное получилось.

## Красные флаги

| Мысль | Что на самом деле |
|---|---|
| «Дирижёр закрылся, значит работает» | Дирижёр видел код, а не работающее приложение. Шаг 3 не пропускается. |
| «QA дошёл до maxRounds, дефекты мелкие» | Мелкие или нет — решает человек, и только если ты их назвал. |
| «Тесты зелёные, поднимать не буду» | Зелёные тесты и живой сервер — разные утверждения. |
| «Соннет написал, что сделал» | Отчёт агента — не доказательство. Доказательство — вывод команды. |
| «Задачи пересекаются, но агенты аккуратные» | Два писателя в одном файле затрут друг друга. Волны существуют ровно для этого. |
| «Заодно закоммичу» | Коммит и пуш — только по отдельной просьбе человека. |
| «QA вернул clean» | Сначала посмотри `coveredAllDimensions` и `closedBy`. Отчёт по трём измерениям из четырёх — не «чисто». |
| «Передам args строкой, там же JSON» | `args` передаётся настоящим объектом. Строка рассыплется по символам, и воркфлоу уйдёт работать с настройками по умолчанию. |
